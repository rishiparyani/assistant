# Setup: accounts, secrets, deploys, limits

What exists outside the repo, where each secret lives, and how code gets deployed. Read this before touching deploys, secrets or CI. The repo is **public**: also read [security.md](security.md#public-repository).

## How deploys work

Agents (Claude Code, Codex) never deploy from their own session and never hold the Cloudflare token.

1. Agent pushes code to GitHub.
2. `.github/workflows/deploy.yml` runs: install → typecheck, lint, test → create the environment's D1 database if missing (`assistant-dev` / `assistant`) and fill its id into `wrangler.jsonc` → create the summaries queue and its dead letter queue if missing (`summaries-dev` / `summaries`, plus `-dlq`) → build → apply D1 migrations → `wrangler deploy` (from `apps/web`, which bundles the Worker and the web app) → smoke test. Pushes that only touch docs, tasks, spikes or Markdown don't deploy.
3. It uses the repository secrets below and the GitHub Environment `production` (main) or `dev` (other branches).

`.github/workflows/ci.yml` runs the same checks plus a build on pull requests, with no secrets.

| Push to                       | Deploys to                          | Database                |
| ----------------------------- | ----------------------------------- | ----------------------- |
| `main`                        | **prod** Worker `assistant`         | prod D1 (real data)     |
| any other branch in this repo | **dev** Worker `assistant-dev`      | dev D1 (fake data only) |
| pull request from a fork      | **nothing**; tests only, no secrets | none                    |

Manual run: Actions → Deploy → Run workflow (pick the branch). Needed when a push changes no deployable files, e.g. creating a branch at an existing commit.

Rollback: redeploy an earlier commit from the Actions tab, or `wrangler rollback`.

## Domain gigspree.in (owner, once)

The Worker routes (`routes` with `custom_domain` in `apps/worker/wrangler.jsonc`) make the DNS records and certificates on deploy; the owner only moves the domain to Cloudflare.

1. Cloudflare dashboard → **Add a domain** → `gigspree.in` → **Free** plan. Cloudflare shows two nameservers.
2. At the registrar where the domain was bought → the domain's **Nameservers** → **Custom** → paste Cloudflare's two → save. Wait for Cloudflare's email or the domain showing **Active** (minutes to a few hours).
3. Cloudflare → gigspree.in → **DNS** → delete any records for `gigspree.in`, `www` or `dev` that were imported from the registrar (parking pages); the deploy creates its own.
4. Google Cloud → Google Auth Platform → **Clients** → the web client:
   - **Authorized JavaScript origins**: add `https://gigspree.in` and `https://dev.gigspree.in`.
   - **Authorized redirect URIs**: add `https://gigspree.in/auth/callback/google`, `https://dev.gigspree.in/auth/callback/google`, `https://gigspree.in/api/admin/drive/callback`, `https://dev.gigspree.in/api/admin/drive/callback`.
   - Keep the old workers.dev entries until the move is done.
5. If a deploy says the API token can't edit the domain: Cloudflare → My Profile → API Tokens → edit the deploy token → add **Zone → Workers Routes → Edit** and **Zone → DNS → Edit** for `gigspree.in`.

After the move, people sign in again on gigspree.in, passkeys are added again (they belong to a domain), and the Home Screen app is re-added from gigspree.in (then turn notifications on again).

Spike deploy (T00): `.github/workflows/spike-t00.yml` runs on pushes touching `spikes/t00/**` from any branch. It creates the `assistant-spike` D1 database if missing, fills its id into `wrangler.jsonc` at build time, applies migrations, deploys, sets secrets, and smoke-tests.

Not secret, fine to commit: D1 database names and IDs, Worker names, the public app URL. They can't be used without the API token.

## Phone app (Expo, `apps/mobile`)

No accounts beyond Apple's (below). Locally: `pnpm --filter @assistant/mobile start` (Expo dev server; press `w` for the web target, `i` for the simulator on a Mac) with `EXPO_PUBLIC_API_URL=http://localhost:8787` and `pnpm dev` running. Sign in on the local server with the test email/password (`apps/mobile/test/seed.mjs` makes a person with fake data and prints the cookie). `pnpm --filter @assistant/mobile build:web` bundles the website target into `apps/mobile/dist`. On a Mac, `pnpm --filter @assistant/mobile ios` runs `expo prebuild` + Xcode for the simulator (`apps/mobile/ios` is generated and git-ignored). CI does the same on GitHub's Mac runners (`.github/workflows/ios.yml`): simulator screenshots on PRs (the app signs in through its `/test` route, which works only against localhost), TestFlight on `main`. A nightly check (`.github/workflows/prod-check.yml`) curls the real app and goes red (GitHub emails the owner) if it doesn't answer.

## Android app

No account needed (decision 2026-10-22 "Android builds too"). The Android workflow (`.github/workflows/android.yml`) runs on GitHub's Linux runners after each push to `main` that touches the app (and by hand from any branch: Actions → Android → Run workflow): `expo prebuild` makes the native project on the runner, Gradle builds a release APK with the JS bundled in, and the APK is the run's artifact **gigspree-android** (download it from the run's page, copy the `.apk` to the phone, open it, allow installs from that source once). It talks to the real server (`https://gigspree.in`; dev builds from other branches to `https://dev.gigspree.in`).

Without signing secrets the APK is signed with the project's debug key: fine for trying it out, but a phone won't update a debug-signed build with one signed by another key, and the Play Store needs the owner's key. When the owner wants a lasting key, once, on any machine with Java:

```
keytool -genkeypair -v -keystore gigspree.keystore -alias gigspree -keyalg RSA -keysize 2048 -validity 10000
base64 -w0 gigspree.keystore   # macOS: base64 -i gigspree.keystore
```

then add these GitHub Actions secrets (never in chat or the repo; keep the keystore file somewhere safe, it can't be made again):

| Secret                      | What                                              |
| --------------------------- | ------------------------------------------------- |
| `ANDROID_KEYSTORE_B64`      | The keystore file, base64 (the second command)    |
| `ANDROID_KEYSTORE_PASSWORD` | The keystore password keytool asked for           |
| `ANDROID_KEY_ALIAS`         | `gigspree` (the alias given to keytool)           |
| `ANDROID_KEY_PASSWORD`      | The key's password (the same unless told keytool) |

Play Store listing later: a Google Play developer account (one-time fee) and an AAB instead of an APK (`:app:bundleRelease`); not needed to install the app by hand.

## Free-tier limits

**GitHub Actions:** public repo = unlimited minutes. If the repo is made private: 2,000 min/month on the free plan (a CI + deploy run is ~2–3 min; nightly backup ~1 min). Over the limit, with the default $0 spending limit, workflows stop until the next month; nothing is charged and the live app keeps running.

**Cloudflare Workers + D1 free plan** (per day, reset 00:00 UTC = 05:30 IST): 100,000 Worker requests; 10 ms CPU per request; D1 5 million rows read, 100,000 rows written; 5 GB total D1 storage. Over the limit on the free plan, requests fail until reset; nothing is charged. Upgrade path: Workers Paid, $5/month. Keep usage low: index every filtered column, never scan whole tables, no polling from clients.

Check current numbers in Cloudflare's and GitHub's docs before relying on them; they change.

## Google Drive backups (owner, once)

1. Google Cloud console → the project used for Google sign-in → search **Google Drive API** → **Enable**.
2. **Google Auth Platform** (or APIs & Services) → **Clients** → the web client → **Authorized redirect URIs** → add `https://gigspree.in/api/admin/drive/callback` and `https://dev.gigspree.in/api/admin/drive/callback` → **Save**.
3. In the app: Settings → **Admin panel** → **Backups** → **Connect Google Drive** → choose the account → allow. Backups then run every night; "Back up now" runs one immediately.

Restore: Admin panel → Backups → **Restore from a file** (owners only). It only adds what's missing.

### Encrypting the backups (owner, once; recommended)

With a key set, every backup in Drive is sealed (AES-256-GCM) and unreadable without it, so a leaked Drive file gives nothing away.

1. Make a key on your laptop: `openssl rand -base64 32` (any long random string works). **Keep it in your password manager**: a restore needs the same key, and nobody can recover a backup without it.
2. GitHub → the repo → Settings → Secrets and variables → Actions → **New repository secret** → name `BACKUP_KEY`, value the key → Add. The next deploy sets it on the Worker (dev and prod both use it).
3. Admin panel → Backups shows **Encrypted** once it's live; the next nightly file ends in `.json.gz.enc`.

Restore of an encrypted file uses the Worker's key by itself. A file made with an earlier key, or restored on another Worker, needs that key typed in the **Backup key** box next to Restore.

## Google Calendar connector (owner, once)

Lets each person connect their own Google Calendar (Connections in the app): the assistant reads it when asked and proposes new events as cards.

1. Google Cloud console → the project used for Google sign-in → search **Google Calendar API** → **Enable**.
2. **Google Auth Platform** → **Data access** → **Add or remove scopes** → tick `.../auth/calendar.events` (or paste `https://www.googleapis.com/auth/calendar.events`) → **Update** → **Save**.
3. **Clients** → the web client → **Authorized redirect URIs** → add `https://gigspree.in/api/connectors/google-calendar/callback` and `https://dev.gigspree.in/api/connectors/google-calendar/callback` → **Save**.
4. While the app's audience is **Testing**, only the test users can connect: **Audience** → add each person's Google address. Calendar is a "sensitive" scope, so Google shows an "unverified app" screen to them (tap **Continue**) until the app is verified; verification is needed before opening it to the public.
5. In the app: the home's "What it remembers" card → **Connections** → **Connect** next to Google Calendar → choose the account → allow.
